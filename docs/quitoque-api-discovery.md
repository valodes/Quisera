# Quitoque API discovery

Checked on 2026-11-14 against the only approved base URL, `https://app.quitoque.fr/api/v2`. Test credentials were read from local environment variables; their values were not printed or added to this document. A user-provided OpenAPI 3.0.2 file was inspected locally and was not copied into the repository.

## Authenticated recipe catalog observed

- `GET /api/v2` with `Accept: application/ld+json` returned HTTP 200 and an API Platform `Entrypoint`. It advertises `product` at `/api/v2/shop/products`; it does not advertise a recipe resource.
- `POST /api/v2/shop/authentication-token` with JSON email and password returned HTTP 200 and string-valued `token`, `customer`, and `refresh_token`. TLS verification was explicitly enabled. The Bearer token is accepted by protected reads. The connector logs neither credentials nor tokens and keeps the short-lived token in memory only.
- `GET /api/v2/shop/orders?page=1&itemsPerPage=100` returned HTTP 200 with a JSON array. Authenticated order objects include `id`, `tokenValue`, `deliveryDate`, `periodStartDate`, and `periodEndDate`. `deliveryDate` is the actual cycle anchor; the other dates are used only to locate the recipe catalog for enrichment.
- The supplied OpenAPI defines the order delivery date as a date-time. The live response used a `YYYY-MM-DD 00:00:00` representation; Quisera validates the civil-date prefix and rejects invalid values rather than substituting a weekday or current date.
- Authenticated `GET /api/v2/shop/orders/{tokenValue}/items?page=1&itemsPerPage=100` returned the actual selected order items. Recipe lines contain `id`, `quantity`, `productName`, and a `variant.product` with product `id`, family attributes, and sometimes image paths. Order-item order is preserved. The private order token is used only for the request and never persisted, returned, or logged.
- In the inspected current delivery, nine recipe-family item rows matched product IDs in the associated dated catalog across its pages. This verifies the observed enrichment join, not a guarantee that every future selected product will exist in the catalog response. An unmatched selected recipe remains a named unavailable snapshot when the order item supplies a name.
- The documented `GET /api/v2/shop/products/{startDate}/{endDate}` with `Accept: application/json`, `format=api`, `page=1`, `itemsPerPage=30`, and `attributes[family][1]=recipe` returned HTTP 200. The JSON envelope has `products`, `paginator`, and `filters`; paginator keys observed are `nbResults`, `nbPages`, `currentPage`, and `maxPerPage`. All 30 bounded results on the inspected page had the recipe family.
- The live recipe product fields include `id`, `code`, `name`, `description`, `image`, `total_time`, `preparation_time`, `ingredients`, `cupboard_ingredients`, `preparation_steps`, `categories`, `tags`, `nutri_score`, `carbon_score`, and `nutritional_datas`. `categories` and `tags` are JSON-encoded arrays with named objects. The stable external key used for deduplication is the returned `code`.
- `ingredients.standard` is an array of objects with `name`, `quantity`, and `unit` among other fields. `cupboard_ingredients` is a JSON-encoded array of named items. `preparation_steps` is a JSON-encoded object with a `Default` locale; numbered steps contain `title` and `description`, followed by a `conclusion` object. The implementation preserves supplied text and order, and does not invent absent content.
- `nutri_score` and `carbon_score` are objects keyed by a letter-grade field in the observed representation. Nutri-Score is imported only when the key is an A–E grade. Carbon score is deliberately not imported or shown because the observed response does not establish its calculation method or reference system. Difficulty is also left unavailable because no verified mapping was found.
- The recipe collection's `image` value is only a storage-path fragment; resolving it at the site root returned HTTP 404. The documented `GET /api/v2/shop/products/{code}` returns `images[]` with an image `id` and a working `/media/image/...` `path` (HTTP 200, JPEG).
- The OpenAPI documents `GET /api/v2/shop/product-images/{id}?filter=...`, including thumbnail and cover filters. The `sylius_shop_product_thumbnail` filter returned a same-origin `media/cache/resolve/...` path; the image returned HTTP 200 as JPEG after a same-origin redirect. Other tested thumbnail and cover filter paths also returned HTTP 200.
- Delivery sync stores only selected recipe snapshots for the order, including full image paths and API-generated thumbnail paths when resolved. This snapshot is not inserted into the recipe library.
- `total_time` is text. On the inspected 30-recipe page, 28 values matched the strict integer-minute format and were parsed; unrecognized formats remain unavailable. The implementation does not substitute `preparation_time` for total duration.
- The dated product collection without the recipe-family filter returned market products, not a suitable recipe catalog. The filtered, dated collection is used only to enrich products already present in the selected order items; it is not bulk-imported.
- The JSON-LD context and authentication response's `Link` header identify `/api/v2/docs.jsonld` as API documentation. That URL returned HTTP 403 to TLS-verified requests with and without Bearer authorization.
- The user-provided `?ui=re_doc` URL returns the entrypoint unless requested with `Accept: text/html`; in HTML mode it serves ReDoc with the full OpenAPI 3.0.2 document embedded in the page. The embedded spec is exactly equal to the user-provided `openapi.json` (154 paths, 180 operations, 698 schemas). Its page config references `/api/v2/docs?format=json`, which also returned HTTP 403. `/api/v2/index.json` returns a `resourceNameCollection`, not OpenAPI; requesting it with an OpenAPI media type returns HTTP 406. `/api/v2/index.html` serves the API Platform Swagger UI.
- The OpenAPI has no recipe-named path. The product schema has optional recipe content, and the dated product collection documents a recipe family filter. Live requests now verify that this filter returns populated recipes.
- `GET /api/v2/shop/products/nextweeks/{firstDay}/{maxWeek}` is documented but unnecessary for the verified manual sync path. Its date argument format remains unspecified and is not used.
- Generic product collection, variants, customer addresses, and unrelated operations are not used by planning sync. No writes, cart changes, payments, account changes, or order modifications were attempted.
- The OpenAPI is available in the user-provided local file and embedded in the ReDoc HTML served by the approved API host. The embedded OpenAPI 3.0.2 document was identical to the supplied file (154 paths, 180 operations, 698 schemas). `/api/v2/docs?format=json` returned HTTP 403; `/api/v2/index.json` is a resource collection, not OpenAPI.

## Limits

The recipe catalog, authentication flow, pagination envelope, ingredient/tag/category shape, step shape, Nutri-Score representation, full image path, and thumbnail filter were verified with authenticated live reads. The numerical semantics of nutrition fields, carbon-score methodology, difficulty mapping, and Quitoque's rate limits remain unverified. On 2026-11-18, the first orders page took 17.7 s and 25.8 s in two authorized reads; an isolated end-to-end internal sync then returned HTTP 200 with 124 delivery rows and no invalid dates. The connector now caps each HTTP attempt at 45 s, retries at most twice for transient network failures and HTTP 408/429/500/502/503/504, honors `Retry-After`, and caps each sync operation at 120 s. Other HTTP errors and invalid response schemas are not retried.

Only retain selected order-item rows independently identified as recipe family, with their order date and verified catalog enrichment. Do not treat the product catalog as the set of selected meals. Do not infer a format for `firstDay`. Keep carbon unavailable until its method and reference system are verified. Do not store raw authenticated responses, credentials, concrete order dates, recipe contents, customer identifiers, or other personal data in this document.
